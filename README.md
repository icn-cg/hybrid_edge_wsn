# Hybrid Edge Wireless Sensor Network

A graduate Wireless Sensor Networks project for experimentally studying how edge aggregation
changes bandwidth use, latency, and reliability as a hybrid network scales and communication
degrades.

The current implementation is **Phase 1: local software foundation**. It provides a versioned
sensor protocol, a bounded concurrent TCP gateway, seeded synthetic sensor nodes, and
automated local-network tests. It does not yet include persistence, aggregation, an upstream
collector, experiment orchestration, analysis, or working ESP32 firmware.

## Research question

> How does edge aggregation affect bandwidth usage, latency, and reliability as a hybrid
> wireless sensor network scales and experiences degraded network conditions?

Secondary measurements planned for later phases include gateway CPU/memory use, aggregation
window tradeoffs, node failure/recovery detection, and controlled communication impairment.

## Architecture

The protocol and gateway are developed locally first so progress does not depend on Raspberry Pi
or ESP32 availability.

```text
Physical nodes (future)                         Mac collector (future)
BME280 -> ESP32 -- Wi-Fi/TCP --+                         ^
                               |                         |
Virtual nodes -- TCP ----------+-> Raspberry Pi gateway-+
       (implemented)                 (runs on macOS now)
                                       validation
                                  aggregation/health (future)
```

Physical and virtual nodes use the same newline-delimited JSON (NDJSON) application protocol.
`node_kind` identifies whether data is physical or synthetic; the gateway's framing and
validation path is otherwise identical.

## Phase 1 behavior

- `asyncio` TCP server: concurrent clients without one thread per node.
- Correct stream framing: split and coalesced TCP reads do not change message boundaries.
- Pydantic protocol validation with strict version, type, identity, timestamp, sequence, and
  environmental-value constraints.
- Safety boundaries: 64 KiB maximum message size, 30-second idle timeout, malformed-message
  isolation, and graceful client/server shutdown.
- Gateway receive metadata: wall-clock milliseconds, monotonic nanoseconds, and application bytes
  read (including the NDJSON delimiter).
- Reconnecting virtual node with seeded synthetic readings, startup delay, artificial delay, and
  application-message suppression controls.
- Automated coverage for protocol failures, hostile/abrupt clients, stream framing, receive
  metadata, and 10 simultaneous nodes.

Synthetic readings contain a baseline, slow sinusoidal drift, and small seeded random noise. They
are labeled `"node_kind":"virtual"` and must not be presented as physical measurements.

## Protocol version 1

One compact JSON object followed by `\n` is one application message. A TCP read is not assumed to
equal one application message.

```json
{
  "type": "reading",
  "version": 1,
  "node_id": "virtual-001",
  "node_kind": "virtual",
  "sequence": 0,
  "timestamp_ms": 1786482001123,
  "temperature_c": 23.82,
  "humidity_pct": 47.31,
  "pressure_hpa": 1012.4
}
```

Heartbeat messages use the same identity/timing fields with `"type":"heartbeat"` and no sensor
payload. Sequence numbers are non-negative and monotonically generated by a node. Gap, duplicate,
and out-of-order classification belongs to the Phase 2 node registry.

The byte counters here represent bytes written at the application layer, not TCP/IP packet counts.

## Requirements and setup

- Python 3.12 or newer (validated with Python 3.13.13)
- macOS or Linux for local development
- Git
- PlatformIO and ESP32/BME280 hardware are not required until the physical-node phase

Create an isolated environment and install the pinned dependencies:

```bash
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

If `python3.13` is unavailable, substitute any Python executable at version 3.12 or newer.

## Run the gateway and a virtual node

From the repository root, start the gateway:

```bash
source .venv/bin/activate
python -m gateway.server --host 127.0.0.1 --port 8662
```

In a second terminal, send five seeded synthetic readings:

```bash
source .venv/bin/activate
python -m virtual_nodes.node \
  --node-id virtual-001 \
  --host 127.0.0.1 \
  --port 8662 \
  --interval 1 \
  --samples 5 \
  --seed 662
```

The gateway logs node ID, message type, sequence, gateway receive timestamp, and application byte
count. Stop the gateway with Ctrl-C. For a future gateway on another host, use its reachable IP;
do not expose the unauthenticated Phase 1 listener to an untrusted network.

The equivalent commands were manually smoke-tested with three readings. The gateway received
sequences 0, 1, and 2 and shut down cleanly.

## Test and quality checks

```bash
source .venv/bin/activate
python -m pytest -q
ruff check .
```

The current suite has 19 passing tests. Integration tests bind ephemeral loopback ports and include
10 concurrent virtual nodes sending three readings each, plus reconnect behavior when the gateway
becomes available after the node starts.

## Clock and latency methodology

Sensor messages carry a sender wall-clock timestamp. At validation, the gateway adds both a
wall-clock receive timestamp and a monotonic timestamp. Same-host virtual-node tests can derive
one-way application latency under a common wall clock; monotonic timestamps support durations
measured entirely at the gateway.

Future physical-node one-way latency will only be reported after explicit clock synchronization,
or it will be labeled approximate. Round-trip measurements are preferred where synchronized clocks
cannot be verified.

## Hardware and PlatformIO status

The planned physical deployment is three ESP32 nodes with BME280 environmental sensors over Wi-Fi
to a Raspberry Pi gateway. The existing `firmware/` files are placeholders from repository
initialization; they are intentionally not claimed as runnable in Phase 1. Firmware will use
PlatformIO/C++, never Arduino IDE. Local `firmware/include/secrets.hpp` is ignored by Git, and a
documented example will be added with the firmware implementation.

## Experiments and results status

No scientific experiments have been run and there are no findings yet. Phase 3 will add a
configuration-driven runner that preserves raw measurements and exact configuration under
`results/raw/<experiment-id>/`; analysis will consume those files directly. Hardware measurements,
synthetic measurements, application-message suppression, and real network packet loss will remain
explicitly distinguished.

Planned study groups are scalability, aggregation-window tradeoff, failure/recovery, and degraded
communication. Results will use repeated trials and report variability rather than relying on one
run.

## Current limitations and next milestone

Phase 1 intentionally has no authentication/TLS, durable storage, sequence-state registry, node
health model, upstream forwarding, aggregation, system metrics, or experiment runner. Generated
synthetic values are plausible test signals, not a model of any specific environment.

The next milestone is Phase 2: registry and sequence tracking, configurable ONLINE/SUSPECT/OFFLINE
liveness, raw persistence, aggregation, and an independent upstream collector with end-to-end tests.
